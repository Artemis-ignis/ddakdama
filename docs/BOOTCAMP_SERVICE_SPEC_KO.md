## 1. 문제 정의 (Day2 적용)

### 1-1. 문제 정의문

> **AI가 추천해준 쇼핑 목록을 실제로 사려는 사람**이
> **쿠팡에서 각 품목을 다시 검색할 때**
> **규격·함량·포장 단위를 항목마다 다시 해석하고 비교해야 하는 재작업**을 겪고 있고,
> 그 결과 **잘못된 규격·수량을 담거나, 귀찮아서 구매를 포기하는 일**이 반복된다.

### 1-2. 좋은 문제 정의 체크리스트 대조 (Day2 p30)

| 조건 | 딱담아 적용 | 충족 |
|---|---|---|
| 고통(Pain) | 품목마다 검색→규격 해석→비교→담기를 반복. 5종 목록이면 수십 분 소요 | O |
| 빈도(Frequency) | 장보기·영양제·생필품 재구매는 주기적. AI 추천 사용 자체가 증가 추세 | O |
| 지불 의사(Willingness) | 쿠팡 파트너스 전환 수수료라는 기존 지불 구조가 이미 존재 | O |
| 재미·가치(Value) | "목록 → 검토 → 장바구니"가 한 번에 끝나는 시간 절약 가치 | O |

### 1-3. 5Why — 표면 문제에서 근본 원인으로

| 단계 | 질문 | 답 |
|---|---|---|
| 현상 | 왜 AI가 짜준 목록대로 사는 게 귀찮은가? | 품목마다 쿠팡에서 다시 검색해야 해서 |
| Why-1 | 왜 다시 검색해야 하는가? | AI 답변과 쿠팡 상품 목록 사이에 연결고리가 없어서 |
| Why-2 | 왜 연결고리가 없는가? | 자연어 목록을 상품 SKU로 변환하는 단계가 없어서 |
| Why-3 | 왜 변환이 어려운가? | "100mg 240정"처럼 함량·포장·실물수량이 한 문장에 섞여 있어서 |
| Why-4 | 왜 섞인 표현이 위험한가? | 잘못 해석하면 240정 1통을 240개로 담는 등 실제 금전 손실로 이어져서 |
| 근본 | **확률적 언어 해석과 결정적 상업 행위 사이에 검증 경계가 없다** | → 딱담아가 만드는 것이 바로 이 경계 |

### 1-4. JTBD (Day2 p53 템플릿)

> **"AI가 장보기 목록을 만들어준 상황"에서**
> **[AI 쇼핑 추천을 실제 구매로 옮기려는 쿠팡 사용자]는**
> **[다시 검색·비교하는 재작업 없이 정확한 장바구니를 얻는 결과]를 위해**
> **[딱담아]를 고용한다.**

기능 중심 관점("장바구니 자동 담기 봇")과의 차이: 딱담아의 Job은 '자동화'가 아니라 **'검증된 전환'**이다. 사용자가 고용하는 이유는 손가락 노동을 없애기 위해서이지, 판단을 위임하기 위해서가 아니다.

| 단계 | 목록 획득 | 검색·비교 | 장바구니 담기 | 검토 | 결제 |
|---|---|---|---|---|---|
| 사용자 행동 | AI에게 목록 요청 | 품목별 쿠팡 검색, 규격 대조 | 후보 중 선택해 담기 | 장바구니 재확인 | 직접 결제 |

## 2. 고객 가설과 검증 (Day3 적용)

### 2-1. 원인 가설 vs 해결책 가설 (Day3 p30)

| 구분 | 가설 | 검증 방법 | 상태 |
|---|---|---|---|
| 원인 가설 | "목록→구매 재작업의 핵심 원인은 규격·수량 해석의 반복이다" | 유저 인터뷰·설문 | 부분 검증 — 고정 목록 5종 회귀 테스트에서 100mg/240정 분리 필요성 확인 |
| 해결책 가설 | "구조화된 계획 + 후보 검토 + 승인 담기면 재작업이 사라진다" | 행동 검증 (실제 MVP 사용) | 진행 중 — 공개 베타 배포, 실사용 지표 수집 전 |

### 2-2. 가설 조건 (Day3 p33 — 대상·개입·측정결과·기준선·기간)

**H1 (활성화 가설)**: AI로 쇼핑 목록을 얻은 사용자가 딱담아에 목록을 붙여넣으면, **첫 세션에서 장바구니 담기 완료까지 도달하는 비율이 60% 이상**일 것이다. (기준선: 수동 전환 시 품목당 3~5분 → 목표: 5종 목록 10분 이내 완료, 2주 내 측정)

**H2 (정확성 가설)**: 규격·포장이 섞인 목록(5종·실물 7개)에서 **사용자 수정 없이 정확한 수량 계획이 생성되는 비율이 80% 이상**일 것이다. (기준선: 수동 해석 시 묶음 오류 경험, 목표: EXACT 자동 선택 정확도)

**H3 (신뢰 가설)**: 사전검사(preflight)에서 가격 미확인·품절·옵션 필요를 걸러내면, **사용자가 결과 화면에서 "잘못 담겼다"고 보고하는 비율이 5% 미만**일 것이다.

### 2-3. 우선순위 — MoSCoW + RICE 혼합 (Day3 p51~58)

| 기능 | MoSCoW | R | I | C | E | RICE |
|---|---|---|---|---|---|---|
| 목록 파싱(규격·수량 분리) | Must | 1000 | 3 | 90% | 2 | 1350 |
| 후보 검색·EXACT/REVIEW 분류 | Must | 1000 | 3 | 80% | 2 | 1200 |
| 사전검사(가격·재고·옵션) | Must | 1000 | 3 | 80% | 1.5 | 1600 |
| 장바구니 delta 검증 | Must | 1000 | 2 | 90% | 1 | 1800 |
| ChatGPT 앱 페어링 | Should | 600 | 2 | 80% | 1.5 | 640 |
| 다중 스토어 어댑터 | Could | 400 | 2 | 50% | 3 | 133 |
| 가격 히스토리·대체품 추천 | Could | 300 | 1.5 | 50% | 2 | 112 |
| 자동 결제 | Won't | — | — | — | — | (안전 경계상 제외) |

*Reach는 분기당 예상 사용자, Effort는 인월(person-month) 기준의 상대 추정.*

### 2-4. Kano 분류 (Day3 p55)

- **Must-be**: 정확한 파싱, 장바구니 오담기 방지, 결제 수동 유지 — 없으면 즉시 이탈
- **Performance**: 후보 검색 커버리지, 처리 속도, 가격 정확도 — 높을수록 만족 비례
- **Attractive**: ChatGPT에서 바로 목록 전송, 부분 실패 복구 경로 — 있으면 감동

## 3. 비즈니스 설계 (Day4 적용)

### 3-1. Lean Canvas (Day4 p16~17)

| 블록 | 딱담아 |
|---|---|
| **문제** | ① AI 추천 목록을 실제 구매로 옮기는 재검색 노동 ② 규격·함량·포장·수량 해석 오류 ③ 자동화 도구의 오담기·결제 불안 |
| **고객군** | 얼리어답터: ChatGPT로 쇼핑 루틴을 짜고 쿠팡에서 사는 20~40대. 확장: 정기 재구매 가구 |
| **고유 가치 제안(UVP)** | "목록을 붙여넣으면, 검토 가능한 쿠팡 장바구니가 된다" — 해석은 AI가, 승인은 사람이 |
| **솔루션** | 목록 구조화 파서 → 후보 비교 → 사전검사 → 승인 담기 → 수량 delta 검증 |
| **채널** | ChatGPT 앱 스토어, Chrome 웹스토어, 바이럴(목록 공유), 콘텐츠(장보기 자동화) |
| **수익원** | 쿠팡 파트너스 전환 수수료(투명한 opt-in). 장기: 프리미엄(가격 추적·대체 추천) |
| **비용 구조** | Cloudflare Workers 운영비, 개발·유지보수, Chrome 스토어 등록, 마케팅 |
| **핵심 지표** | 목록→담기 완료율, EXACT 자동 선택 정확도, 주간 재사용률, 파트너스 전환율 |
| **경쟁 우위** | 확률적 해석과 결정적 검증의 분리 아키텍처 + 수량 계획 도메인 로직(묶음·함량·포장 독립 모델링) — 단순 "AI 장바구니 봇"이 따라하기 어려운 검증 경계 |

### 3-2. 벤치마킹 (Day4 p22~31)

| 서비스 | 배운 점 | 딱담아 적용 |
|---|---|---|
| 쿠팡 정기배송·다시담기 | 재구매 마찰 제거가 핵심 가치 | 재구매 목록의 구조화·재사용 |
| Honey·가격비교 확장 | 확장 프로그램은 "구매 직전"에 개입할 때 가치가 큼 | 장바구니 담기 직전 사전검사 |
| 직접 장바구니 자동화 스크립트 | 검증 없는 자동화는 오담기·계정 위험 | 승인 게이트 + delta 검증 + CAPTCHA 미우회 |
| 실패 사례(각종 쇼핑 봇) | 결제까지 자동화하면 신뢰·정책 문제 | 결제는 영구 수동 — 신뢰 경계를 제품 원칙으로 |

### 3-3. PSF → PMF (Day4 p33~43)

- **PSF 확인 대상(얼리어답터)**: "ChatGPT로 장보기 목록을 만들고 쿠팡에서 사는 사람" — 이미 AI 추천 + 수동 검색이라는 임시방편을 쓰고 있으며(PAIN), 시간을 쓰고 있고(BUDGET), 불완전한 초기 버전도 쓸 집단(TOLERANT)
- **PMF 신호(Sean Ellis)**: "딱담아를 더 이상 쓸 수 없다면?" → "매우 아쉽다" 40% 이상을 목표
- **현재 단계**: MVP 공개 베타 — PSF 정성 확인 단계. PMF는 재사용률·NPS로 측정 예정

### 3-4. MVP → MLP (Day4 p46~51)

- **MVP 범위(현재 v1.0.2)**: 목록 파싱, 후보 검색·분류, 사전검사, 승인 담기, delta 검증, 부분 실패 복구 — "가설을 행동으로 확인하는 최소 기능"
- **MLP 요소**: 다크모드 위젯, 실제 담긴 가격 합계 표시, 새 목록 시작 흐름 — "다시 쓰고 싶은" 경험
- **의도적 제외**: 자동 결제, CAPTCHA 우회, 쿠키 수집 — 검증이 아니라 신뢰 붕괴를 부르는 기능

## 4. 성장 지표 — AARRR/RARRA (Day5 적용)

### 4-1. 퍼널별 핵심 질문과 지표 (Day5 p21, p54)

| 단계 | 핵심 질문 | 딱담아 지표 |
|---|---|---|
| **Retention** | 다시 쓰는가? | 주간 재사용률(목록→담기 2회+), 월간 리텐션 |
| **Activation** | 첫 가치를 경험하는가? | 첫 세션 담기 완료율, Aha 도달률 |
| **Referral** | 추천하는가? | 목록 공유·초대 발생률, NPS |
| **Revenue** | 돈이 되는가? | 파트너스 전환율, 건당 수수료 |
| **Acquisition** | 어떻게 유입되는가? | ChatGPT 앱 설치→페어링 전환율, 채널별 유입 |

### 4-2. Aha Moment (Day5 p37~38)

**"목록을 붙여넣었더니 5종·실물 7개로 정확히 구조화되고, 100mg과 240정을 구분해 보여준 순간"** — 사용자가 "이건 다르다"고 느끼는 지점. Activation 지표는 이 순간까지의 도달률로 정의한다.

### 4-3. North Star Metric (Day5 p28~30)

> **주간 "검증 완료 담기" 수 (Weekly Verified Adds)**

- 사용자 가치(정확한 장바구니)와 비즈니스 가치(파트너스 전환)가 동시에 움직이는 지표
- Input metrics: 목록 파싱 성공률, EXACT 비율, 사전검사 통과율, 담기 승인율
- 매출을 North Star로 쓰지 않는 이유: 수수료는 전환율·단가 등 외부 변수에 흔들려 원인 분해가 어렵다 (Day5 p30)

## 5. 서비스 구조 (Day6 적용)

### 5-1. 3단 구조 — 사용자 / 파트너스 / 관리자 (Day6 p35~47)

| 면 | 역할 | 딱담아 구현 |
|---|---|---|
| 사용자 서비스 | 목록 입력·검토·승인 | ChatGPT 앱 위젯 + Chrome 사이드 패널 |
| 파트너스 | 상품 데이터·전환 | 쿠팡 파트너스 API(승인 대기) + 일반 검색 fallback |
| 관리자 | 운영·지원 | 지원 인박스(support-inbox), 레이트리밋·격리 모니터링 |

같은 "장바구니 계획" 데이터가 세 면에서 다르게 보인다: 사용자는 후보·가격·수량, 파트너스는 상품·전환, 관리자는 handoff 상태·오류.

### 5-2. AI 서비스 구조 — 해석과 검증의 분리 (Day6 p49~60)

- **GPT-5.6 (확률적 해석)**: 자연어 목록 → 구조화 도구 호출. "무엇을 원하는지"를 이해
- **packages/core (결정적 검증)**: 단위 분류·수량 계획·매칭·카트 계약. "정확히 무엇을 담는지"를 결정
- **HITL 경계**: EXACT만 자동 선택, REVIEW는 사용자 확인, 결제는 항상 수동 — Day6의 "골든셋·HITL 검토 기준을 기획자가 설계"를 그대로 구현
- **환각 방지**: 검색 결과가 없으면 NONE으로 표시하고 수동 검색 경로 제공 — AI가 상품을 "지어내지" 못하는 구조

## 6. 제품 원칙과 UX (Day7 적용)

### 6-1. Golden Circle (Day7 p9)

- **Why**: AI가 똑똑해져도 "사는 행위"의 마지막 판단은 사람에게 남아야 한다는 신념
- **How**: 확률적 해석과 결정적 검증을 분리하고, 모든 상업 행위에 승인 게이트를 둔다
- **What**: 쇼핑 목록을 검토 가능한 쿠팡 장바구니로 바꾸는 ChatGPT 앱 + Chrome 확장

### 6-2. UX 심리학 법칙 적용 (Day7 p42~50)

| 법칙 | 딱담아 적용 |
|---|---|
| Jakob's Law | 쿠팡 검색·장바구니라는 익숙한 패턴 위에 구축 — 새 인터페이스 학습 불필요 |
| Hick's Law | 후보를 EXACT/REVIEW/NONE 3종으로만 분류 — 선택지 인지 부담 축소 |
| Fitts's Law | 승인·담기 버튼을 사이드 패널 하단 고정 — 반복 조작 동선 최소화 |
| Miller's Law | 목록을 품목 단위 카드로 청킹 — 한 번에 하나씩 검토 |
| Peak-End Rule | 완료 화면에 실제 담긴 가격 합계·장바구니 바로가기 — 마지막 경험을 "확인됨"으로 설계 |

### 6-3. UX 라이팅 원칙 (Day7 p32~34)

- 명확함: "담기" 전에 "사전검사 결과"를 먼저 보여주는 2단계 확인
- 간결함: 서버 URL·토큰·내부 ID를 사용자 화면에 노출하지 않음
- 유용함: 실패 시 "왜 안 됐는지 + 어떻게 복구하는지"를 같은 화면에 표시

## 7. 기술 구조 (Day8~10 적용)

### 7-1. 클라이언트·API·서버·DB (Day8)

| 계층 | 기술 | 역할 |
|---|---|---|
| 클라이언트 | Chrome MV3 사이드 패널(React), ChatGPT 앱 위젯 | 목록 입력, 후보 비교, 승인 |
| API | MCP(Model Context Protocol), REST | 도구 호출, 페어링, handoff |
| 서버 | Cloudflare Workers + Durable Objects | 공개 엔드포인트, 페어링 코드, 격리 |
| 공유 코어 | packages/core (순수 TypeScript) | 파서·수량 계획·매칭·카트 계약 |
| 저장 | chrome.storage.local(저널), DO(단기 handoff) | 작업 재개, TTL handoff |

### 7-2. 백엔드 선택 근거 (Day10 p17~25)

Firebase/Supabase 대신 **Cloudflare Workers + Durable Objects**를 선택한 이유:

- handoff는 TTL이 있는 단기 상태 — RDBMS 스키마보다 키-값 + 만료가 적합
- MCP 엔드포인트는 전 세계 엣지에서 낮은 지연이 필요
- 다중 사용자 격리를 DO의 단일 스레드 모델로 구현 — Day11의 "DB 접근 권한" 문제를 구조적으로 축소

### 7-3. 바이브코딩 프로세스 (Day9~10)

- Codex로 저장소 분석→파서·수량 계획 설계→상태머신 구현→회귀 테스트 생성
- 모델/Effort: 구조 설계·보안 경계는 고추론, 반복 UI 수정은 균형 모드
- Day10의 "캡처→수정 요청" 사이클을 실제로 적용: Playwright 스크린샷으로 UI 상태를 확인하며 반복

## 부록. 배운 것 (What we learned)

에이전틱 쇼핑에서 가장 어려운 부분은 추천 생성이 아니라, **확률적 언어 이해와 실제 상업 행위 사이의 투명한 검증 경계**를 만드는 것이다. 자연어 해석은 유연하게 두되, 상품 식별·수량·가격·장바구니 변경은 결정적이고 관찰 가능하게 만들어야 한다 — 이것이 Day1~12 전체를 관통하는 "이해는 아웃소싱할 수 없다"의 실천이다.
